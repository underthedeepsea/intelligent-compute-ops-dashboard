# Monitoring v1 implementation contract

Scope: per cluster, separate persistent CSV snapshot from inspection cache. Current API envelope/schema_version 1.0 preserved; API paths under /api/v1/monitoring/. Admin writes; catalog_admin/operator reads; templates available to both read roles. All scope checks use AccessScope environment_code; screen_viewer sees screens only.

## HTTP

* GET /monitoring/clusters -> data.items each `{id,code,name,environment_code,region,version,monitoring_source,source_generation,snapshot:{id,sampled_at,imported_at,endpoint_count,hardware_count}|null,endpoints:[...],hardware:[...]}`. endpoint config exposes id/code/name/role/service/model/pd names and codes, current engine binding id/version/provider id/environment_id/engine identity/scope; hardware exposes id/code/name/resource_type/provider_id/environment_id/asset_id/host_id/gpu_uuid/version. No credential_ref/base_url_ref. GET scope includes only enabled same-environment entities.
* GET /monitoring/options -> data `{providers:[{id,code,name,environment_code}],models:[...],services:[...],pd_groups:[...]}` admin-only, or use paginated existing catalog APIs for these safe choices.
* PATCH /monitoring/clusters/<uuid>/source body `{expected_version:int,source:"INSPECTION"|"CSV"}` -> updated cluster summary. Same source is no-op. Source mode edit must use shared switch function, including generic catalog PATCH if allowed there.
* GET /monitoring/templates/<kind>.csv where kinds `cluster-config`, `endpoint-metrics`, `hardware-metrics`; returns UTF-8 BOM CSV attachment and Content-Type text/csv. Templates have one example row (clearly marked as example on page); example codes are editable.
* POST /monitoring/imports/validate body `{kind,cluster_id?:uuid,csv:string}` -> `{valid:true,row_count,summary,expected_version:int|null,normalized_hash}`. For new cluster-config cluster_id omitted. Client keeps original CSV and this response. All errors normal API envelope `{error:{code,message,details:{rows:[{row,field,message}]}}}`; cap displayed errors 50.
* POST /monitoring/imports/apply body `{kind,cluster_id?:uuid,csv:string,expected_version:int|null,normalized_hash:string}` -> `{changed:boolean,row_count,cluster:<summary>}`. Parse/revalidate server-side under lock; hash is integrity guard, not authorization. Config creation requires expected_version null; existing cluster update and metric import require exact current cluster.version. Increment version on changed import. Repeated exact current snapshot hash returns changed=false (after authorization and target equality), including retry carrying prior expected_version; conflicting content + stale expected_version -> 409.
* Inspection binding editor can use existing POST/PATCH /catalog/engine-bindings and /catalog/hardware-bindings, supplied safe provider choices and endpoint IDs, required expected_version on edits. Hardware gains cluster_id. Do not put secrets or freeform upstream URLs in monitoring UI.

## CSV columns

cluster-config (one cluster per file; flat endpoint rows):
`environment_code,cluster_code,cluster_name,region,model_code,model_name,service_code,service_name,deployment_mode,pd_group_code,pd_group_name,endpoint_code,endpoint_name,role,runtime_code,pod_uid,pod_name,namespace,workload_ref,node_uid,node_name,observed_at`

- one endpoint per row; optional runtime group describes one configured member. A CLUSTER-only row with endpoint_code and downstream fields empty is valid for empty new cluster. All cluster identity cells repeated consistently; environment and cluster_code immutable for update. Existing model/service/PD code means same-environment matching relationship only; missing creates named entries. Repeated model/service/PD definitions must match. Do not disable omitted existing entities: config import is additive/upsert only. Reject conflicting endpoint codes belonging to a different cluster, cross-env code collisions, duplicate endpoint or runtime codes, invalid combined/split roles. Existing entity names can be changed only when they are cluster-owned endpoints/runtime; shared model/service/PD conflicting names are validation errors to avoid surprising other clusters. New creates use CONFIGURED origin. No source switching in config import. Missing runtime fields are not invented. Engine and hardware inspection mapping uses explicit UI editor above.

endpoint-metrics (requires existing selected CSV cluster):
`endpoint_code,sampled_at,ttft_avg_ms,ttft_p90_ms,ttft_p95_ms,ttft_p99_ms,tpot_avg_ms,tpot_p90_ms,tpot_p95_ms,tpot_p99_ms,e2e_avg_ms,e2e_p90_ms,e2e_p95_ms,e2e_p99_ms,ttft_e2e_ratio,request_rate,request_rate_per_minute,generated_tokens_per_second,input_tokens_per_second,kv_cache_hit_ratio,running,waiting`

hardware-metrics (selected CSV cluster; snapshots need no Provider/HardwareBinding):
`resource_code,resource_name,resource_type,host_id,gpu_uuid,sampled_at,utilization_ratio,temperature_celsius,memory_used_bytes,memory_total_bytes,cpu_busy_ratio,memory_available_bytes`

- resource_type GPU_POOL or HOST, strict required identity shape; GPU requires gpu_uuid, host forbids gpu_uuid. For metrics only applicable family columns may have values. Blank numeric fields represent MISSING, never zero. All populated metrics finite nonnegative, ratios 0..1; counts integers; percentile ordering for populated complete triples; memory used/available <= total and total > 0 for derived fraction.
- All nonempty rows must share one timezone-aware sampled_at <= now+30 sec; no age cutoff. One endpoint/resource per row, no duplicate identities. At least one valid numeric metric per row. Endpoints must be enabled and in the selected cluster.
- Each kind atomically replaces that kind's current cluster snapshot, preserving other kind. Separate sampled_at/hash/imported_at per kind avoids mislabelling untouched hardware after endpoint import. One empty data file must fail (no implicit clear).

## Persisted and projection shape

KubernetesCluster fields monitoring_source INSPECTION(default)|CSV, source_generation positive int default 1 noneditable. ClusterCsvSnapshot one-to-one cluster, endpoint_payload/hardware_payload JSON, respective hash/sampled_at/imported_at; payloads latest only, per-file <=1 MiB, <=1000 rows, normalized total bounded (e.g. 2 MiB/cluster). Separate endpoint/hardware import generation/hash. HardwareBinding nullable cluster FK for migration, clean verifies same environment. New monitoring editor requires cluster; null legacy hardware never joins managed-cluster display.

CSV endpoint projection keeps existing endpoint shape, `data_state:"CSV_SNAPSHOT",status:"UNKNOWN"`; observation `{source_type:"CSV",data_state:"CSV_SNAPSHOT",sampled_at,imported_at,source_window:{start:sampled_at,end:sampled_at},origin:"CSV",source_generation,snapshot_id,upstream_status:"UNKNOWN",transport_status:"NOT_APPLICABLE"}`. Values use existing metric shape AVAILABLE/MISSING. Hardware likewise has cluster_id, source_type, data_state and UNKNOWN status. Inspection projections add source_type INSPECTION and cluster_id; retain expiry/trust rules. No CSV value labelled FRESH, VERIFIED or live healthy. Endpoint omitted from current CSV has MISSING, no fallback to inspection. A cluster switched back to inspection does not expose CSV payloads. Snapshot persists in DB while hidden, so switching to CSV restores last uploaded snapshot until next import; label and actual sampling time always visible.

Mixed screen-level source_type MIXED, pure CSV source_type CSV, pure inspection INSPECTION. Root CSV_SNAPSHOT only when relevant displayed data is CSV (no new freshness privilege for arbitrary MIXED). Frontend per-observation CSV exception bypasses 300s expiry ONLY when source_type==CSV && data_state==CSV_SNAPSHOT; no global live-provider exemption. Historical chart API never returns inspection history while cluster CSV; return one CSV point or empty with explicit CSV_SNAPSHOT coverage. Health/alarms stay UNKNOWN for CSV.

## Atomicity and lifecycle

Reuse Revision lock as global serialization anchor, then cluster lock, then dependent bindings. Source switch bumps cluster.version+source_generation, engine/hardware binding versions, resets PollState and HardwareObservation for those bindings, audits and bumps metadata/telemetry. Switching back also invalidates previous inspection observations. Poll candidate filtering and pre-request recheck require enabled endpoint/cluster + INSPECTION. Every source switch increments dependent binding_version, including CSV→inspection→CSV switches; captured binding_version is checked at success publication AND completion/error update, together with current cluster enabled/source state. This reuses existing same_generation binding/provider logic and prevents ABA acceptance without a separate worker token. Generic catalog source edit must call same switch path or be forbidden. Endpoint.cluster reassignment invalidates its binding generation; hardware.cluster reassignment increments binding generation as existing save does. Disabled cluster/endpoint prevents display and new poll. Worker must not publish late old-source success/error into new-source state.

CSV validate does no writes. Apply repeats full validation before any writes inside outer transaction; catalog.save nested transactions may be reused; any row failure rolls all changes back. Hash computed over canonical typed values and resolved target IDs, not raw text; duplicate files line ending/BOM differences become no-op. Authorization before hash/idempotency responses. Reject unknown/duplicate headers, oversized UTF-8 BOM-compatible input, NUL/control data, Excel formula-prefixed free text; do not echo whole raw rows in audits. Audit only kind/hash/row count/affected IDs/version and source switch old/new. CSRF/session boundaries unchanged. Provider URL whitelist and backend credential env remain enforced.
